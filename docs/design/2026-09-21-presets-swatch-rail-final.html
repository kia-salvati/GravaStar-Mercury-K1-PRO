Presets — swatch rail, final reference

The chosen presets screen for the Lighting area of apps/web, rebuilt so that hovering, arrowing and clicking never fight each other and never rebuild the DOM. Hover or arrow down the squares to preview on the silhouette and the field; click to select; Apply writes all three blocks with per-block progress (~2 s, the strip is inert meanwhile); Escape returns the preview to what the keyboard reports. The frame meter below is live in your browser: press Stress to sweep the ten squares for two seconds and read the worst frame.

What changed since v2, and why it was stuck

  1. Hover landed on the selected preset, not the hovered one. Every preview change rebuilt the whole frame, then restored keyboard focus to the selected square; that programmatic focus() fired focusin, which set the preview back to the focused square. After any real click (which focuses the square) no hover could win. → Preview no longer rebuilds anything, and focus restoration runs with a guard that the focus handler respects.
  2. Lag: a full DOM rebuild per hover (rail, field, strip, silhouette with 85 rects, panel) — 3–10 ms of main-thread work each, 11 rebuilds for a 10-square sweep, 34 for 30 arrow presses. → One structural render only when the list, selection, mode or apply state changes; preview updates mutate existing nodes: 84 fill attributes, three text nodes, four CSS variables. Preview work is coalesced to one requestAnimationFrame; clicks are synchronous and flush the pending preview.
  3. The field restarted its keyframes on every hover because the field element was recreated. → One persistent field with one layer per motion; all layers animate continuously, only the layer named by data-fx is visible. A preview change is four variable writes and one attribute.
  4. Enter/leave flapping: the tooltip was a child that could take the pointer, and each square handled its own leave. → Tooltip is pointer-events:none; one pointerover on the strip starts a preview, one pointerleave of the strip ends it; focusin/focusout on the strip mirror it for the keyboard.
  5. Escape rule was implicit. → Escape clears the preview and the selection, so the panel shows what the keyboard reports — unless the selected preset is what the keyboard reports, in which case the selection stays. Written into the state notes below.
  6. Apply had no progress and the strip stayed live. → Apply runs three blocks with write + 500 ms settle each (~2 s); the sheet shows each block pending → writing → settling → verified with a bar; the strip is inert and dimmed until Done.

State

presets:    Preset[]            // for this keyboard's uuid, max 10, in saved order
selectedId: id | null           // the square with the outline; owns Apply / Rename / Delete
previewId:  id | null           // the square under the pointer or with focus; never persisted
mode:       null | 'replace'    // Save current at 10 of 10
renamingId: id | null
applying:   null | { presetId, blocks: [{ name, status: 'pending'|'writing'|'settling'|'verified' }] }
current:    Lighting            // what the keyboard reports (from useKeyboard)

shown = preset(previewId) ?? preset(selectedId) ?? current
state text = previewId && previewId !== selectedId ? "previewing — not written"
           : selectedId ? (equals(preset, current) ? "selected · matches the keyboard" : "selected — not written")
           : "keyboard now"

Rules

  • pointerover on a square → previewId = id (idempotent; fires again for children). pointerleave of the strip → previewId = null. Never per-square leave.
  • focusin on a square → same as pointerover; focusout with relatedTarget outside the strip → same as strip leave. Programmatic focus restoration sets a guard so it does not preview.
  • click → selectedId = id; previewId = null, synchronous structural render, then the pending preview is flushed. Click on the add square → save (or enter replace mode at 10).
  • Escape → previewId = null; selectedId = equals(selected, current) ? selectedId : null; focus stays where it is. In replace mode Escape cancels the mode first.
  • Arrow Up/Down, Home, End move focus between squares (preview follows focus). Enter/Space is the click.
  • While applying: strip has inert, sheet cannot be dismissed, no preview changes are accepted.
  • Preview render is scheduled with requestAnimationFrame and coalesced; there is no timer-based debounce anywhere. Toast auto-dismiss is the only timer besides the simulated write.

Components

  • PresetStrip — the glass column: squares + add square + count. Props: presets, selectedId, current, mode, count; events: select(id), preview(id|null), save(). Owns the pointer/focus handlers and arrow-key roving.
  • PresetSquare — swatch (single / mixed / none / per-key grid), current dot, tooltip (pointer-events none), number + name at ≥ 700 px.
  • PresetPreview — head (name + state), Silhouette, readline. Receives shown; updates by mutation: a ref to the 84 rects, set fill/fill-opacity; no re-mount on preview change (in React: memoised rect list, an effect that writes attributes, or a plain DOM ref).
  • PresetDetail — name (or rename input), saved date, Apply / Rename / Delete for the selected preset; Export / Import.
  • Sheets — ConfirmApply, ApplyProgress (three block rows + bar, Done when all verified), ConfirmDelete, ConfirmReplace, Import (free-slot tally, disabled while over). Focus in on open, back to the opener on close, Escape closes except ApplyProgress.
  • Field (existing component) gains data-fx and the layered structure; it must not be keyed on the effect.

Keyboard-only vs pointer

  • Pointer: hover preview, tooltip, click select, scrim to close sheets.
  • Keyboard: arrow / Home / End roving in the strip, focus preview, Enter select, Escape revert, Tab trapped inside sheets, Enter / Escape in rename.
  • Both: every action button, Export / Import, Done.
